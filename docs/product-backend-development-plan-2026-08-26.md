# 算得清后续开发计划

**版本基线：**最新预览已同步并重启，当前版本为 `d3766e97`。  
**规划目标：**在不破坏现有账本、成本诊断、订单/SKU、导出、工作区和私有媒体能力的前提下，将“算得清”推进为一款拥有统一品牌体验、可扩展账户体系、可维护后端和隐私优先数据分析能力的商家成本产品。

## 一、现状与规划原则

当前项目已经具备 React/TypeScript 前端、Express/tRPC 服务、Drizzle/MySQL 数据层、工作区、个人/店铺资料、邮箱密码注册登录、自托管初始化管理员、私有媒体、主题皮肤、健康检查与非 root 生产运行能力。[1] [2] 因此后续工作不应重新建设账号、工作区或账本基础，而应围绕**体验统一、权限边界、可观测性和可演进性**补齐产品能力。

> 先确保用户能安全、顺畅地进入并完成第一笔账；再建设后台、开放接口和分析能力。不能让后台扩张先于核心经营闭环。

| 原则 | 具体含义 |
|---|---|
| 账本优先 | 所有 UI、API 和数据分析都不得改变金额精度、会计角色、聚合日期或历史快照。 |
| 体验与安全同时前置 | 登录验证码、限流、会话、隐私提示和最小化数据采集必须与界面同时设计。 |
| 管理后台独立 | 店铺经营端保持轻量；运营/管理员能力通过受控后台路由和管理员权限提供。 |
| 渐进开放 | 先稳定内部 tRPC 契约；公开 API 只在审计、权限、限流和版本控制齐备后开放。 |
| 可回滚 | 每个阶段都有迁移、埋点、UI 文案和灰度开关，避免一次性覆盖全部用户体验。 |

## 二、优先级总览

| 优先级 | 工作流 | 解决的问题 | 前置依赖 |
|---|---|---|---|
| P0 | 设计基础与账户入口 | 配色、主题、品牌、登录和首次引导不统一，影响首次信任与留存 | 设计令牌、账号流程决策 |
| P0 | 首次经营闭环 | 新用户不知道先做什么，难以快速得到成本诊断 | 工作区/行业已有能力可复用 |
| P1 | 用户与权限管理 | 用户、店铺、成员和操作边界缺少可视化管理 | 角色模型、审计日志 |
| P1 | 模块维护与管理后台 | 缺少版本状态、迁移状态、故障定位和配置管理入口 | 管理员路由、事件模型 |
| P2 | 数据分析与产品洞察 | 缺少激活、使用、留存与数据质量的聚合视图 | 隐私策略、事件字典、授权提示 |
| P2 | 对外 API | 缺少与 POS、电商平台或内部工具的受控连接能力 | API 版本、授权范围、限流、审计 |

## 三、阶段 0：产品与安全决策冻结

本阶段不大规模写页面，而是把后续最容易返工的边界锁定下来。

| 决策项 | 推荐方案 | 验收条件 |
|---|---|---|
| 登录识别 | 保留现有邮箱密码登录；新增“邮箱验证码”作为验证/找回/高风险操作的第二能力，而不是立即替换密码登录。 | 明确验证码使用场景、有效期、发送频率、失败次数、找回流程和关闭入口。 |
| 验证码通道 | 第一阶段优先邮件验证码；短信验证码作为后续通道适配层，而非同时上线。 | 确认 SMTP 或邮件服务商、发信域名、退信处理和运营成本；未确认前不把验证码做成不可用的 UI。 |
| 主题范围 | 主题分为“亮/深模式”和“品牌皮肤”，颜色令牌由系统管理，用户只选择经过可读性验证的组合。 | 所有语义色在亮/深模式下有同一含义；不允许任意颜色导致风险、成功和主操作含义漂移。 |
| 吉祥物 | 仅用于首次引导、空态、完成里程碑和登录欢迎面；不进入高频账本录入和成本诊断核心屏。 | 吉祥物不遮挡数字、图表、操作和错误提示；支持降低动态效果。 |
| 数据分析隐私 | 只采集产品交互事件和匿名/聚合统计，默认不上传交易金额、商户名称、订单备注、图片或凭证内容。 | 形成事件字典、保留周期、删除策略与管理员访问规则。 |

## 四、阶段 1：UI 品牌系统与首次体验

### 1. 设计系统升级

建立一套跨登录、引导、账本、分析和后台复用的设计令牌。现有品牌蓝、成功绿、预警橙、风险红和图表深色模式可作为基础；新的工作应集中在**页面背景、表面层级、文字、边框、输入、按钮、状态和动效**的统一，而不是重绘每个页面。

| 子项 | 实施内容 | 验收标准 |
|---|---|---|
| 配色 | 建立语义令牌：`brand`、`surface`、`ink`、`muted`、`line`、`success`、`warning`、`danger`；为亮/深模式提供成对值。 | 账本收入、成本风险、成功操作、禁用状态在五个一级页语义一致。 |
| 主题风格切换 | 将现有皮肤选择升级为“系统亮/深 + 经认证品牌皮肤”的两层结构，保存到用户/工作区偏好。 | 刷新、重新登录和跨设备后能恢复；深色下输入、图表 Tooltip、导出和弹层均可读。 |
| Logo | 拆分“算得清产品标识”和“店铺标识”：产品 Logo 始终用于登录、引导和导航；店铺 Logo 用于工作区身份。 | 不再由商家名称替代产品识别；小尺寸、深色和上传店铺 Logo 均可用。 |
| 吉祥物 | 设计一个可静态展示的轻量角色，提供欢迎、空账本、完成第一笔账、达成目标四种状态。 | 只在低频时刻出现；资源使用外部托管且不造成首屏加载阻塞。 |

### 2. 登录、验证与首次引导

现有自托管访问页已支持登录、创建店铺、行业选择和密码规则。[1] 第一轮应先优化这一条真实路径，不直接新增独立的“登录页原型”。

```text
欢迎与品牌信任
      ↓
登录 / 创建店铺
      ↓
邮箱验证或安全验证（仅在需要时）
      ↓
店铺名称 + 行业 + 经营目标（可跳过非必要项）
      ↓
第一笔收入或成本
      ↓
成本诊断初始结果
```

| 场景 | 页面/行为 | 关键数据与安全要求 |
|---|---|---|
| 登录 | 精简为邮箱、密码、忘记密码、创建店铺；品牌与吉祥物只做辅助。 | 会话续期、登录失败限流、通用错误文案，避免泄露邮箱是否注册。 |
| 注册 | 保留姓名、店铺、行业；将可选资料移到引导后。 | 密码策略、邮箱验证状态、工作区创建必须原子化。 |
| 邮箱验证码 | 用于邮箱确认、找回密码、修改安全设置和异常登录验证。 | 验证码哈希存储、短有效期、发送与验证限流、一次性消费、审计日志。 |
| 首次引导 | 三步以内：确认行业模板 → 录入一笔 → 看第一条成本结论。 | 所有步骤可跳过、稍后继续；不伪造账本或示例经营数据。 |

## 五、阶段 2：用户、店铺与权限管理

用户管理必须服务“一个人、多店铺、未来可邀请成员”的真实路径，而不是先建设复杂组织后台。

| 能力 | 第一版范围 | 后续扩展 |
|---|---|---|
| 个人账户 | 姓名、头像、邮箱验证状态、密码修改、登录设备与退出。 | 两步验证、设备信任、账号注销导出。 |
| 店铺工作区 | 店铺名称、行业、Logo、默认货币/时区、主题偏好。 | 多工作区切换、连锁店汇总。 |
| 成员角色 | `owner`、`manager`、`staff` 三类；默认只开放 owner。 | 精细到模块/数据范围的权限。 |
| 邀请 | 邮箱邀请、到期、撤销、接受后加入工作区。 | 团队审批与审计。 |
| 审计 | 登录、角色变更、邀请、导出、数据删除和 API 密钥操作。 | 可筛选的管理员审计台与风险告警。 |

现有工作区和用户资料接口应延伸为明确的 tRPC 契约；新增字段按 schema → migration → DB helper → router → UI → test 的顺序实施，避免只在前端保存偏好。[2]

## 六、阶段 3：模块维护与可视化管理后台

经营端不应出现运营配置。建议新建仅管理员可访问的管理后台，界面以状态和操作为核心，不做 BI 大屏。

| 管理模块 | 管理员看到的内容 | 首版操作 |
|---|---|---|
| 用户与店铺 | 用户状态、工作区、行业、最后登录、角色、验证状态。 | 搜索、冻结/恢复、角色变更、查看审计。 |
| 模块版本 | 当前前端/服务版本、数据库迁移、功能开关、发布日期。 | 查看状态、灰度启停、回滚指引；不能直接修改账本数据。 |
| 系统健康 | API 健康、数据库连通、队列/媒体错误、最近发布状态。 | 只读诊断、跳转日志、管理员通知。 |
| 内容配置 | 公告、首次引导文案、吉祥物展示条件、行业模板版本。 | 草稿、预览、发布、回滚和审计。 |
| 数据质量 | 未分类流水、缺供应商支出、缺成本 SKU、重复导入风险等聚合数量。 | 导出问题清单、跳转相应工作区；不替用户修改数据。 |

模块更新采用**版本化配置 + 功能开关 + 可回滚迁移**。数据库结构变更仍必须走 Drizzle migration；展示和文案可通过有版本的配置表管理；行业模板升级需要显示升级说明并保留原账本历史引用。

## 七、阶段 4：数据分析与隐私优先事件体系

数据分析分为两个层次：商家自己的经营分析继续基于其账本数据；产品运营分析只使用受控事件和聚合指标，两者绝不混用。

| 分析层 | 事件/指标 | 禁止采集 |
|---|---|---|
| 产品激活 | 完成注册、完成验证、创建店铺、录入第一笔账、首次打开成本诊断。 | 金额、分类名称、商户、备注、图片。 |
| 功能使用 | 访问模块、执行导出、打开成本诊断、完成引导、切换主题。 | 完整业务对象和私有媒体 URL。 |
| 数据质量 | 缺供应商关联的支出数、无分类记录数、无成本 SKU 数，以工作区匿名聚合。 | 原始账单明细。 |
| 可靠性 | API 错误码、页面性能、上传失败类型、发布版本。 | 密码、验证码、访问令牌、身份文件。 |

管理台的首版指标应覆盖新增工作区、激活率、首笔账完成率、7/30 天回访率、模块使用占比、导出成功率和失败率。每个指标必须标注事件定义、时间窗口、去重规则和数据更新时间。

## 八、阶段 5：对外 API 与集成能力

当前 tRPC 接口适合内部 Web 应用；若未来接入 POS、电商平台或第三方财务工具，建议单独建设 `/api/v1` 公共 API，而不是直接暴露内部 tRPC 过程。

| API 域 | 第一版端点方向 | 安全要求 |
|---|---|---|
| 工作区与资料 | 只读店铺资料、行业与偏好。 | OAuth/API Key 二选一、workspace scope、审计。 |
| 账本导入 | 创建草稿流水、批量校验、错误返回。 | 幂等键、字段白名单、金额精度校验、限流。 |
| 经营读取 | 已授权期间的聚合指标、成本诊断摘要。 | 不返回私有附件、密码、令牌和未授权分类明细。 |
| Webhook | 导入完成、成员邀请、导出准备完成。 | 签名、重放防护、失败重试、事件版本。 |

公开 API 的前置条件是：角色/范围模型完成、审计日志可用、速率限制可用、版本文档可用、错误码可用，以及数据删除/撤销授权链路可用。若这些条件未满足，仍仅维护内部 tRPC 接口。

## 九、推荐实施顺序

| 阶段 | 交付物 | 为什么排在这里 |
|---:|---|---|
| 0 | 登录验证码渠道决策、隐私事件字典、主题/品牌令牌规范。 | 避免后续登录、后台和数据分析反复改数据模型。 |
| 1 | 设计系统、产品 Logo、登录/注册优化、首次引导、第一笔账闭环。 | 最直接提升新用户信任、激活和留存。 |
| 2 | 邮箱验证、密码找回、用户/店铺/成员基础管理和审计。 | 先建立身份和权限基础，后续后台和 API 才安全。 |
| 3 | 管理后台、功能开关、模块版本、系统健康和数据质量视图。 | 支持持续发布、问题定位与可回滚维护。 |
| 4 | 产品事件与聚合分析面板。 | 基于稳定账户和事件字典建设可信指标。 |
| 5 | 公开 API、API Key/OAuth、Webhook 和导入集成。 | 最后开放外部边界，降低安全与兼容风险。 |

## 十、每阶段共同验收门槛

每次实施都必须通过以下门槛：不改变账本金额与聚合口径；新增 schema 有迁移和回滚说明；权限错误不泄露资源是否存在；验证码、会话、令牌和媒体不进入日志或分析事件；亮/深模式可读；375px、390px、430px、768px、1280px 验证；Vitest、TypeScript、生产构建、生产健康接口与容器非 root 身份验证通过。

## 十一、建议先确认的两项产品决策

开始实现前，需要优先确认两项会改变技术方案的选择：

1. **验证码通道：**是否先采用邮箱验证码？如果要短信验证，需要明确短信服务商、签名与发送地区。
2. **后台使用者：**管理后台仅供项目 owner 使用，还是需要给店铺 owner 也提供“店铺管理台”？前者更适合先落地，后者需要更完整的角色和权限模型。
