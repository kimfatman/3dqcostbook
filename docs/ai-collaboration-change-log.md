# AI 协作变更登记规范
**日期：** 2026-09-01 ｜ **适用：** 所有 AI（Trae / Cursor / 豆包 / Copilot 等）对本仓库的代码修改
**目的：** 确保每次 AI 修改后，功能层级表、功能清单矩阵、变更日志同步更新，避免仓库结构混乱、功能遗漏

---

## 一、核心原则

> **AI 修改代码 = 必须登记变更。** 没有例外。
>
> 无论修改大小，只要改变了用户可见的功能、页面、交互、数据结构，就必须更新对应文档。

### 为什么要登记
- 功能层级表是全局地图，不更新就会"地图和 territory 不一致"
- 后续加功能时找不到挂载点，导致重复造轮子或结构混乱
- 无法追溯"这个功能是谁加的、为什么加、加在哪"
- 多人/多 AI 协作时互相覆盖

---

## 二、必须登记的变更类型

| 变更类型 | 是否必须登记 | 登记位置 |
|---|---|---|
| **新增功能**（新页面/新按钮/新弹窗） | ✅ 必须 | 功能清单矩阵 + IA表 + 功能卡片 |
| **修改功能**（改交互/改入口/改布局） | ✅ 必须 | 功能清单矩阵（状态/备注）+ 变更日志 |
| **删除功能**（移除页面/按钮/入口） | ✅ 必须 | 功能清单矩阵（标记已移除）+ 变更日志 |
| **重构**（不改功能只改代码结构） | ⚠️ 视情况 | 如影响入口/层级则登记，否则只记变更日志 |
| **Bug 修复** | ⚠️ 视情况 | 如改变了用户可见行为则登记，否则只记变更日志 |
| **样式微调**（颜色/间距/字号） | ❌ 不登记 | 除非涉及皮肤令牌变更，否则不登记 |
| **文档修改** | ❌ 不登记 | — |
| **依赖升级** | ❌ 不登记 | — |

### 判断口诀
- **用户能感知到的变化** → 必须登记
- **用户感知不到、只是代码内部变化** → 只记变更日志
- **不确定** → 登记（宁可多记不可漏记）

---

## 三、登记流程（AI 必须按此执行）

### 步骤 1：修改前 — 判断变更类型

在开始修改代码前，先回答：
1. 这次修改属于哪种变更类型？（参考第二节）
2. 是否新增了用户可见的功能？
3. 是否改变了现有功能的入口/层级/交互？
4. 是否需要新增数据表/字段/状态？

### 步骤 2：修改中 — 保持结构一致

- 新增页面时，必须挂到现有的 L1-L4 层级下，不要自创平行体系
- 新增功能入口时，必须遵循现有导航模式（底部Tab / 列表页按钮 / FAB / 设置页 / 详情页更多菜单）
- 新增颜色/样式时，必须使用 `--sdq-*` 语义令牌，禁止硬编码颜色
- 新增数据表/字段时，必须在 `cost-book.ts` 中定义类型并处理 `normalizeState` 兼容

### 步骤 3：修改后 — 执行登记（强制）

修改完成、三门禁通过后，**必须**按以下顺序更新文档：

#### 3.1 更新功能清单矩阵

文件：`docs/information-architecture-feature-matrix-2026-09-01.md`

- **新增功能**：在矩阵末尾新增一行，分配下一个 FID（如 F052），填写功能名称/所属页面/L层级/优先级/状态
- **修改功能**：找到对应 FID 行，更新"状态"或"备注"列
- **删除功能**：找到对应 FID 行，状态改为"❌ 已移除"，备注移除日期和原因

#### 3.2 更新信息架构表（IA）

文件：`docs/information-architecture-feature-matrix-2026-09-01.md`

- **新增 L2/L3 页面**：在对应 L1 一级入口下新增一行，填写 L2/L3/L4、功能操作、入口、数据依赖
- **修改入口/层级**：更新对应行的"入口"或"L层级"
- **删除页面**：删除对应行，并在变更日志记录

#### 3.3 创建功能卡片（仅新增功能时）

- 复制 `docs/feature-cards/TEMPLATE.md`
- 保存为 `docs/feature-cards/F0XX-功能名.md`（如 `F052-coupon-management.md`）
- 填写完整卡片内容
- 在功能清单矩阵的"备注"列引用卡片路径

#### 3.4 更新变更日志

文件：`docs/change-log.md`（如不存在则创建）

按日期记录本次变更：

```markdown
## YYYY-MM-DD

### 新增
- F0XX 功能名：一句话描述（提交：xxxxxxx）

### 修改
- F0XX 功能名：修改了什么（提交：xxxxxxx）

### 移除
- F0XX 功能名：移除原因（提交：xxxxxxx）

### 技术
- 重构/依赖升级/性能优化等（提交：xxxxxxx）
```

### 步骤 4：提交 — 提交信息规范

提交信息必须包含：
- 类型前缀：`feat`（新增）/ `fix`（修复）/ `refactor`（重构）/ `docs`（文档）/ `style`（样式）
- 模块：`(ui)` / `(skins)` / `(auth)` / `(ia)` 等
- 一句话描述
- 如果涉及功能登记，在描述末尾加 `(F0XX)`

**示例：**
```
feat(ui): 新增优惠券管理功能 (F052)
- 优惠券列表页（我的→营销工具→优惠券）
- 新增/编辑优惠券表单
- 满减/折扣两种类型
- 已更新功能层级表和功能清单矩阵
```

```
fix(ui): 订单详情SKU字号提升到13px (F005)
- 修复F005订单详情SKU明细字号过小问题
- SKU编码改用等宽字体
- 已更新功能清单矩阵备注
```

### 步骤 5：验证 — 提交前自检清单

提交前必须确认：

- [ ] 三门禁全绿：`pnpm check && pnpm test && pnpm build`
- [ ] 功能清单矩阵已更新（新增/修改/删除对应行）
- [ ] IA 表已更新（如涉及页面层级变化）
- [ ] 功能卡片已创建（如新增功能）
- [ ] 变更日志已记录
- [ ] 提交信息包含 FID（如涉及功能变更）
- [ ] 新增功能使用 `--sdq-*` 语义令牌，无硬编码颜色
- [ ] 新增功能在 5 种皮肤下显示正常（至少验证 soft 和 deep）
- [ ] 新增 ≥1 项回归测试

## 四、AI 启动提示词（必须包含）

每次让 AI 开始修改代码时，在提示词末尾**必须**加上以下段落：

```
【变更登记要求】
本次修改完成后，必须执行以下登记：
1. 读取 docs/information-architecture-feature-matrix-2026-09-01.md，判断本次变更属于哪种类型
2. 更新功能清单矩阵（新增/修改/删除对应行，分配FID）
3. 如涉及页面层级变化，更新IA表
4. 如新增功能，复制 docs/feature-cards/TEMPLATE.md 创建功能卡片
5. 更新 docs/change-log.md 变更日志
6. 提交信息包含FID
未完成登记不得提交。
```

## 五、常见问题

### Q1：只是改了一个按钮的颜色，需要登记吗？
A：不需要。样式微调（颜色/间距/字号）不登记，除非涉及皮肤令牌变更或改变了功能入口。

### Q2：重构了代码但功能没变，需要登记吗？
A：不需要更新功能清单矩阵和IA表，但需要在变更日志的"技术"部分记录。

### Q3：修复了一个Bug，用户行为变了，需要登记吗？
A：需要。找到对应功能的FID，在功能清单矩阵的"备注"列记录修复内容，变更日志记录。

### Q4：新增了一个内部工具页面（用户不可见），需要登记吗？
A：不需要。只登记用户可见的功能。内部工具/开发页面在变更日志"技术"部分记录即可。

### Q5：FID 怎么分配？
A：取功能清单矩阵中最大的 FID 数字 +1。如当前最大是 F051，新增就是 F052。不要跳号、不要复用已删除的 FID。

### Q6：多个 AI 同时修改，FID 冲突怎么办？
A：以先提交的为准。后提交的 rebase 后重新分配 FID。建议每次只让一个 AI 修改功能相关代码。
