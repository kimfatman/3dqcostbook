# 算得清全面项目审计

**审计基线版本：** `93e84541`（账单导出发布前检查点）；本节末尾另记录 P0 修复状态。  
**审计范围：** 经营流水与导出、账本数据保存、认证与媒体、移动端六个关键页面、依赖供应链、生产容器与反向代理。  
**审计结论：** 当前版本的核心路径已具备可用基础，自动化质量门禁与生产健康正常；但在**登录抗暴力破解、并发保存可靠性、依赖升级与生产防护头**方面存在优先级较高的工程风险，建议先完成 P0 再继续扩展业务功能。

## 发现与优先级

| 优先级 | 发现 | 证据 | 风险 | 修复建议与验收标准 |
| --- | --- | --- | --- | --- |
| **P0（已修复，待生产回归）** | 登录、注册和首次初始化没有速率限制、失败冷却、IP/账号维度告警或 CAPTCHA 阈值。 | 原始版本中 `auth.login`、`registerAndCreateWorkspace`、`bootstrap` 均为公共过程且无应用层限流。 | 可被撞库、暴力猜测或批量注册消耗资源。 | 新增同 IP 与身份散列双维度、5 次/15 分钟的单进程失败计数；达阈值返回通用“操作过于频繁”提示，登录失败和注册重复邮箱不泄露账号存在性，成功后清除计数。当前实现的边界是容器重启或多实例不会共享计数，后续扩容时应迁移到 Redis/数据库。 |
| **P0（已修复，待生产回归）** | 账本保存采用“先读取 revision，再条件更新”的乐观锁，但未检查条件更新实际影响行数。 | 原始 `saveWorkspaceBook` 在更新 `workspaceBooks` 后直接写审计并返回 `conflict:false`。 | 两个并发保存窗口可能让后一请求未写入账本却向客户端报告成功，造成静默丢失修改。 | 条件 `UPDATE` 现以 mysql2 `ResultSetHeader.affectedRows === 1` 作为唯一成功条件；0 行时事务中止，随后查询并返回当前 revision，且不会写入工作区时间戳或审计事件。 |
| **P1** | 生产应用与 API 缺少 HSTS、CSP、X-Frame-Options/`frame-ancestors`、X-Content-Type-Options、Referrer-Policy 与 Permissions-Policy。 | Caddy 仅配置压缩与反向代理；公网响应头实测未包含上述策略。 | 增加点击劫持、MIME 嗅探与脚本注入后的影响面。 | 在 Caddy 增加最小安全头；以资源实际来源制定可工作的 CSP，并验证登录、媒体、静态素材与下载不被阻断。 |

| **P1** | 依赖审计存在 19 条高危、47 条中危、8 条低危通告；直接生产依赖包含过期 `axios`、`nanoid`、`drizzle-orm`，新增 `xlsx@0.18.5` 本身没有可用修复。 | `pnpm audit --prod`；高危包还包括间接 `lodash`、`path-to-regexp`、`form-data`。 | 供应链与运行时攻击面扩大；其中 Axios 用于服务端 SDK，Drizzle 用于数据访问。 | 建立可升级矩阵：先升级有兼容修复的直接依赖和 Express 链；评估用维护中的 XLSX 写入库替代 SheetJS 社区版或隔离其输入面；每批升级跑全量测试与生产构建。 |

## 功能与交互审计结论

核心账本、订单/SKU、退款、成本卡、供应商、分类、预算、月报和图表路径均已有领域测试与移动端入口。流水筛选、月份、关键词和导出使用同一当前结果集合；导出字段覆盖日期、类型、分类、金额、供应商、渠道、订单、备注、凭证、状态与流水编号。账期增长系数越界曾导致演示数据出现无效金额，本轮已补回退和初始化修复，相关测试通过。

需要特别注意的是：当前账本主体仍以工作区 JSON 状态保存。该方案便于快速演进，但会使“单条流水级并发、审计、查询性能、精细权限”依赖客户端状态与整本 revision。应先修正 revision 条件更新的原子性，再决定是否将高频流水和订单拆表。

## 视觉与可用性审计结论

当前移动端已形成稳定的白色承载面、蓝色经营结果卡、金融数字等宽字体、紧凑列表和五项底部导航。首页、流水、分析与我的页的信息任务总体可区分；资料读取失败时也有明确重试与返回出口。

后续视觉优化应优先解决数据可信度与长列表效率，不建议重新引入页面网格、装饰性虚线或厚重分隔。首页趋势在没有日数据时需要明确的业务空态；个人中心的主题功能则应收敛，避免与核心经营数据界面产生割裂。

## 建议修复顺序

| 顺序 | 批次 | 目标 |
| --- | --- | --- |
| 1 | 安全与数据完整性 | 登录限流/冷却、账本条件更新原子性、请求体限额。 |
| 2 | 供应链与边界防护 | 依赖升级/替换计划、Caddy 安全头、非 root 容器、OAuth 启动日志收口。 |
| 3 | 经营可信度与性能 | 首页日趋势空态、流水大列表基准与增量加载、生产导出真实验收。 |
| 4 | 自动化门禁 | 并发保存、登录节流、安全头、真实浏览器下载与移动端输入回归。 |

## P0 修复状态（待发布复核）

本次按用户确认的优先级完成了认证和数据完整性修复。密码规则已由“至少 12 位”调整为**至少 8 位、最长 128 位、禁止常见弱口令、纯空白和明显重复/顺序组合**；不再强制人为的“必须大小写/数字/符号”组合，前端改用“建议使用长密码短语”的说明。登录、公开注册和首次初始化各自使用相同的失败冷却策略，限流键同时包含经 Express 可信代理链计算的来源 IP 和单向散列后的身份标识。

账本保存现在只有在条件更新准确影响一行时才更新工作区时间戳和写入 `book.save` 审计事件。竞争失败将回读当前 revision 并返回冲突结果。通用请求体已从 50MB 收紧到 1MB，媒体端点仍保持单独的 5MB 二进制上限。P0 单元与路由回归新增 12 项；在无损合并 GitHub 后续功能后，完整质量门禁为 33 个测试文件、119 项测试，腾讯云 `api.3dq.site/healthz` 返回正常，`app.3dq.site` 返回 HTTP 200，app/Caddy/MySQL 容器均在运行。生产日志中的未配置 OAuth 提示仍列为 P1，不影响本地认证链路。

> 本报告的生产环境核查仅进行健康、响应头、匿名路由和容器状态观察；未读取密码、密钥、数据库明文或真实用户账单内容。生产账单下载与用户设备输入问题被明确列为待验收，而非宣称已通过。
