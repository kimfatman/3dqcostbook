# 算得清 · 计算与输入单元全面审计

**审计日期：**2026-08-21  
**审计范围：**金额、比例、日期、数量、预算、销售目标、成本卡与 BOM、智能定价、订单、退款、退货回收、现金/利润聚合与健康度阈值。  
**审计结论：**账本聚合核心已经具备清晰的分录角色和分（`fen`）存储模型，退款、可售回收成本、毛利与经营利润的基本公式亦已有自动化验证。但是，写入端仍把许多 HTML 输入属性当作唯一防线，服务层未形成统一的有限数、整数、金额精度、比例上限与日期顺序校验。这会造成少数异常输入能够进入本地账本，并进一步影响经营首页、SKU、订单、预算、健康度和报表之间的口径一致性。

> **本轮为审计，不修改任何业务规则或已发布数据。**建议先实施 P0，再以同一套校验器收口 P1；修复必须附带单元测试和现有账本兼容迁移。

## 1. 方法、边界与基线

本次审计沿着“页面表单 → Store 写入方法 → 分录生成 → 指标与图表聚合 → 页面展示”的路径检查。重点比对了 `Home.tsx` 的保存处理、`cost-book.ts` 的状态写入、`ledger-metrics.ts` 的会计聚合、`order-ledger.ts` 的订单/退款分录，以及定价、健康度、图表的派生函数。为避免在审计阶段污染现有本地账本，未通过界面写入故意异常的业务数据；异常结论来自代码路径追踪和可复算边界分析。

当前基线已通过 TypeScript 检查、8 个测试文件共 39 项测试和生产构建。测试已覆盖净营收、退款不进入 COGS、毛利率/经营利润率、期间过滤、预算超支、可售回收成本和渠道预警等核心不变量，但尚未覆盖 Store 写入层的异常输入与编辑同步。[1] [2]

| 核查维度 | 已确认状态 | 审计判断 |
|---|---|---|
| 货币存储 | 主账本以整数分保存，`toFen` 使用四舍五入 | 方向正确；必须在转换前校验有限数与两位小数精度 |
| 利润口径 | 净营收 = 毛销售 + 其他收入 − 退款；毛利和经营利润分别计算 | 公式正确；手工收入的写入角色与该公式不一致 |
| 订单快照 | 下单时冻结 SKU 单价/成本和渠道费用模板 | 正确，历史订单不被后续成本卡或模板修改重写 |
| 退款回收 | 仅“可售回收入库”产生负 COGS 回冲 | 正确，已有自动化测试 |
| 现金流 | 仅根据 `cashDirection` 聚合 | 正确，不混同利润表分类 |
| 异常输入防御 | 主要存在于 HTML `min`、`max`、`step` 或页面简单判断 | 不足；服务层可被直接调用或被旧/损坏 localStorage 绕过 |

## 2. 已验证的计算不变量

账本内核只对 `posted` 分录聚合，并将销售、其他收入、客户退款、COGS 和 OPEX 分开处理。退款主分录只冲减净营收，退款手续费属于经营费用；可售回收的负 COGS 只在明确回收入库时生成。这一设计能够避免“退款同时扣收入又重复扣成本”的常见错误。[1] [2]

订单模型保留了每个 SKU 的成交时单价和单位成本，因而成本卡或 SKU 后续改价只影响随后创建的订单。订单低于保本价和低于目标贡献毛利率的预警，也使用订单创建时的渠道费用快照计算，而不是读取当前模板。[2]

| 规则 | 当前公式/行为 | 审计判断 |
|---|---|---|
| 净营收 | 毛销售 + 其他收入 − 退款 | 正确，已有测试 |
| 毛利 | 净营收 − COGS | 正确 |
| 经营利润 | 毛利 − OPEX | 正确 |
| 预算超支 | 保留超过 100% 的真实占用率 | 正确，不应为视觉方便而封顶 |
| 退款 COGS | 仅 `sellable_restocked` 回冲对应历史单位成本 | 正确 |
| 定价分母 | 平台费率 + 目标贡献毛利率 ≥ 100% 时不可报价 | 正确，但写入端应提前阻止不可用模板 |
| 期间聚合 | `occurredAt` 的 `YYYY-MM` 必须精确匹配 | 正确，但“当前期间”本身被写死 |

## 3. P0：应立即修复的正确性风险

### F-01 手工“收入”被写成销售收入，污染毛销售及跨页销售口径

**证据。**页面的手工收入保存调用 `addRecord`，而 Store 将 `type === "income"` 写为 `eventType: "sale"`、`ledgerRole: "revenue"`。账本内核则将所有 `sale + revenue` 相加为 `grossSalesFen`；只有 `income + other_income` 才会计入 `otherIncomeFen`。[1] [3] 因此，人工登记的租金返还、补贴、利息、其他业务收入等会被当作销售额。

**可复算影响。**订单销售 ¥100，另手工录入“其他收入” ¥50 时，当前实现会显示毛销售 ¥150、净营收 ¥150；订单双轴销售趋势仍只统计订单的 ¥100。首页经营结果与订单销售趋势将出现不可解释的 ¥50 差异。

**修正方案。**应先明确产品语义，再实施其中一个不可混用的方案。推荐将流水类型拆为“销售收入”和“其他收入”：前者明确写入 `sale/revenue`，后者写入 `income/other_income`。若产品决定手工入口仅允许补录销售，应把 UI 文案、筛选标签和帮助文本统一改为“销售收入”，避免用户把非销售收入录入其中。`addRecord` 和 `updateRecord` 必须同时修改，历史记录应通过一次性迁移按原有分类或用户确认进行归类，不能静默重写。

**验收。**新增测试应验证：销售 ¥100 + 其他收入 ¥50 + 退款 ¥10 时，`grossSalesFen=10000`、`otherIncomeFen=5000`、`netRevenueFen=14000`；每日订单销售图只显示 ¥100。

### F-02 退款金额仅校验大于零，允许超过该 SKU 实际成交收入

**证据。**`createRefund` 会校验退款数量不超过可退数量，但只检查 `refundAmount > 0`，随后直接用 `toFen` 写入退款分录；退款页面的金额输入也只有 `min="0.01"`，没有最大值。[3] [4]

**可复算影响。**一件成交价 ¥68 的 SKU 可登记 ¥680 或更高的退款。账本会正常把超额部分从净营收扣除，造成单笔订单、SKU 和当期经营结果为负数且无法从原始交易解释。部分退款时，该风险同样存在。

**修正方案。**服务层必须以冻结成交价为唯一上限，先将输入转为分后比较：`refundFen > 0 && refundFen <= line.unitPriceFen * quantity`。金额和数量均须为有限数；若业务需要“仅退实付金额”，应以订单行保存的实付单价/折后金额为上限，而不是当前成本卡售价。UI 可同步设置 `max` 和默认值，但这只能改善输入体验，不能替代服务层校验。退款日期还应不早于订单成交日期，避免退款被记入销售发生前的期间。

**验收。**覆盖全退、部分退、重复部分退、退款金额等于上限、超一分钱、退款日期早于订单日期、不同月退款等场景。

### F-03 订单与退款数量没有服务层正整数约束，可能生成非整数“分”

**证据。**订单表单虽使用 `step="1"`，但状态更新只做 `Math.max(1, Number(...))`；保存时只保留 `quantity > 0` 的行。Store 的 `addOrder` 与 `createRefund` 均未使用 `Number.isInteger`。[3] [4] 因此，例如 `1.5` 件可以通过写入层；退款表单本身也没有 `step="1"`。

**可复算影响。**数量为 1.5 时，收入、COGS、佣金、履约费和退货回收成本都会按 1.5 倍计算。对于分单位不是整数倍的商品，这会使本应为“分”的 `amountFen` 变成小数，违背统一整数分的账本约定，并使 SKU 销量、退款件数和库存语义失真。

**修正方案。**若 SKU 单位是件、份、次等离散单位，定义共享验证：`Number.isFinite(quantity) && Number.isInteger(quantity) && quantity >= 1`。在 UI 层把退款数量补为 `step="1"`，并对当前输入立即显示“数量必须为正整数”；服务层拒绝不合规写入并返回 `{ ok, reason }`。若未来确需支持千克、米等连续单位，应在 SKU 模型显式增加 `quantityScale` 或 `allowDecimalQuantity`，并为对应单位定义可接受精度及金额分摊规则，不能隐式放开所有 SKU。

**验收。**订单/退款各覆盖 0、负数、0.5、1.5、`NaN`、`Infinity`、正常整数和最大可退数量。

## 4. P1：应在 P0 后统一收口的风险

| 编号 | 发现与影响 | 证据 | 建议修复 |
|---|---|---|---|
| F-04 | 服务层没有统一拒绝 `NaN`、`Infinity`、过多小数和超大金额。`addCard`、`updateCard`、`addRecord`、`updateBudget`、`updateSkuCost` 等大多直接写入；成本卡页面对材料金额检查了有限数，但售价、人工、制造费用没有同等检查。异常值会通过 `calcCard`、`toFen` 或聚合传播为 `NaN`。 | [1] [3] | 抽出 `parseMoney`、`parseNonNegativeMoney`、`parsePercent`、`parsePositiveInteger`、`parseIsoDate` 五个纯校验器。先验证有限数、范围和最多两位小数，再调用 `toFen`。写入方法应返回结果对象，而非静默 `setState`。 |
| F-05 | 渠道佣金率、目标贡献毛利率和健康度阈值只做 `Math.max(0, …)`。通过 Store 直接调用可写入 ≥100% 的比例，定价公式分母为零/负数，健康度配置也会失去百分比语义。 | [3] [5] | 健康度阈值限制为 0–100；渠道单项限制为 0–99.9，且佣金率 + 目标贡献毛利率必须 `< 100`。用户保存时提示具体字段，迁移/读取旧值时才可使用 `Math.min` 防御性修剪。 |
| F-06 | 成本卡和 BOM 的前后端规则不一致。独立 BOM 表单拒绝金额 0，但成本卡整体保存只拒绝材料金额 `< 0`，可保存 0 元材料；成本卡界面要求售价大于 0，详情页却存在“售价未填写/毛利率无法计算”的展示分支。Store 本身完全不校验。 | [3] [4] | 统一业务策略：若材料是实际成本项，统一要求 `> 0`；若允许免费材料，单独标记“赠品/无成本项”且不作为普通材料。明确成本卡是否允许“仅建成本、暂不定价”；若允许，SKU 应禁止下单直至售价完整，而不是写入 0 元单价。 |
| F-07 | `currentPeriod` 固定为 `2026-07`，页面默认日期也固定为 `2026-07-14`。当前截图已显示“电商 · 2026 年 07 月”，而审计日已在 2026 年 08 月。新录入的数据和“本月”预算、目标、趋势、健康度可能落在不同期间。 | [3] [4] | 将默认期间改为本地时区安全的当日 `YYYY-MM`，将默认日期改为当日；保留用户已选期间作为显式状态。所有“本月”入口统一读取同一 `currentPeriod` 来源，并在跨月后刷新。 |
| F-08 | 订单详情与订单列表始终展示退款前的成交额和“订单毛利”，订单贡献利润也不扣已退款/退款手续费；而 SKU、首页和分析页会按退款后的净营收聚合。已退款订单因此无法跨页直接对账。 | [3] [4] | 保留“成交额/成交毛利（退款前）”，但为有退款订单新增“售后后净收入、回收后 COGS、退款手续费、售后后经营贡献”的明确口径。订单列表金额应优先展示成交额并带退款后净额标签，或改为展示净实收，二者不可混名。 |
| F-09 | 手工退款的手续费和回收成本是主分录的关联 extras；编辑主退款仅更新主分录，extras 的金额、日期、类别和现金方向不会同步。结果是同一业务动作跨期间或跨金额不一致。 | [3] | 将退款作为原子业务对象，而非可独立编辑的三条普通流水；或在编辑主记录时联动更新/删除全部 `relatedEntryId` extras。删除逻辑已会删除关联分录，可复用这一关联模型。 |
| F-10 | 日期字段仅作为字符串切片参与期间聚合，订单、退款、流水与归档服务层未验证 `YYYY-MM-DD` 格式、真实日历日期或必要的先后关系。损坏日期会导致“幽灵月份”或遗漏。 | [1] [3] | 服务层校验合法 ISO 日期，并按规则校验退款日期不早于原订单。是否允许未来日期需由产品规则明确；财务已入账流水通常应拒绝未来日期。 |

## 5. P2：已知限制与可规划项

销售目标归档输入使用 `step="0.01"`，但目标随后转换为分存储。当前显示通常可保留两位小数，然而预算编辑只允许整元，两个看似同类的金额入口精度不一致。[3] 建议统一产品规则：如果销售目标与预算按整数元管理，将归档输入改为 `step="1"` 并明确“元”；如果支持角分，预算也应支持两位小数并在所有页面使用同一格式。

退款手续费当前只要求非负，未与退款金额或平台规则建立合理性阈值；手工退款的回收成本也不与订单/SKU 建立关联。这在允许手工调整的原型阶段可以保留，但应在上线真实账本前标注为“人工调整”，并要求备注、凭证或审批状态。

所有写入成功提示都由页面在调用 `setState` 后立即显示。对于纯前端 localStorage 原型，这能提供即时交互反馈；但写入方法没有返回持久化结果，且 `localStorage.setItem` 发生配额或权限异常时 UI 仍会提示成功。后续迁移到微信小程序或云端时，应将“保存成功”绑定到持久化确认，并在重复点击时禁用提交按钮或使用幂等键。

## 6. 推荐实施顺序

第一批应只修复 P0，并保持既有账本聚合公式不变。优先抽取纯校验函数，再改写 `addOrder`、`createRefund`、`addRecord`、`updateRecord` 的返回契约，最后让 `Home.tsx` 根据 `{ ok, reason }` 展示错误或成功。这样可避免“UI 通过、服务层仍写坏数据”的双轨漏洞。

第二批统一 P1 的金额/百分比/日期处理，并明确订单售后后的展示口径。应先为异常写入建立测试，再补 UI `min`、`max`、`step` 和即时错误提示；HTML 属性只是辅助体验，不是数据完整性的边界。

| 实施批次 | 主要文件 | 必须新增的测试 |
|---|---|---|
| P0-A：交易类型与数量 | `cost-book.ts`、`Home.tsx`、新增 `cost-book.validation.test.ts` | 手工其他收入不进入毛销售；订单/退款数量拒绝小数、负数和非有限数 |
| P0-B：退款上限与日期 | `cost-book.ts`、`Home.tsx`、`order-ledger.test.ts` | 单行上限、部分退款、累计可退量、超额一分钱、退款早于订单 |
| P1-A：统一数值防线 | `cost-book.ts`、`pricing.ts`、`health-metrics.ts` | 金额两位小数、`NaN`/`Infinity`、极大值、百分比边界、费率和目标之和 |
| P1-B：成本卡与订单展示 | `cost-book.ts`、`Home.tsx`、`cost-book.test.ts` | BOM 0 金额策略、无售价成本卡策略、退款后订单净额/利润展示 |
| P1-C：时间基准 | `cost-book.ts`、`Home.tsx`、图表/目标测试 | 跨月默认日期、本期自动切换、归档和预算/目标归属一致 |

## 7. 修复后的验收门槛

修复完成前，应维持现有 39 项测试全部通过，并新增覆盖写入端边界的测试。至少应覆盖如下最小矩阵：所有金额的空值、0、负数、两位以上小数、`NaN`、`Infinity` 和超大值；所有数量的 0、负数、小数与最大值；所有百分比的 0、100、超过 100 与两项合计临界值；订单、退款、预算、目标和成本卡在不同月份、不同产业模板及编辑/删除后的聚合结果。

完成代码修正后，需分别验证首页经营结果、订单列表/详情、SKU 指标、分析页、预算、销售目标历史和健康度设置。验收重点不是“表单能保存”，而是同一笔交易在所有页面都以同一个交易类型、同一金额单位、同一期间和同一退款后口径呈现。
