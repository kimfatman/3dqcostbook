# 成本管家迁移部署准备清单

**目标环境：**腾讯云上海 · OpenCloudOS 9 · 4 vCPU / 4 GB RAM / 3 Mbps 公网带宽  
**目标域名：**`3dq.site`（用户确认已备案）  
**推荐应用栈：**Node.js + TypeScript + Docker Compose + Caddy + MySQL + 腾讯云 COS  
**当前状态：**仅完成部署规划；**未连接、未修改服务器、未切换 DNS、未导入任何用户数据。**

> 合规提示：下列备案与对外可访问性说明仅供部署规划参考，不构成法律意见。上线前请以腾讯云控制台、通信管理部门及域名备案主体的实时要求为准，尤其要核对备案主体、域名、网站/应用名称和实际服务器地域的一致性。

## 1. 容量结论与边界

该服务器足以承载成本管家的首期生产闭环：一个 Node.js API、一个 MySQL 实例、一个 HTTPS 反向代理以及基础系统服务。它不应在首期同时承载 Redis、搜索引擎、消息队列、图像转码、复杂监控栈和开发环境，以免 4 GB 内存被常驻服务耗尽。

3 Mbps 理论上约为 **0.375 MB/s**，对应 2 MB、5 MB、10 MB 文件的理论最短传输时间分别约为 5.3 秒、13.3 秒、26.7 秒；真实速度还会受 TLS、网络波动及并发影响。因此，账本 JSON/API 流量可以保留在服务器，凭证图片与将来附件必须直传对象存储，应用服务器只生成受限的签名上传地址和保存文件元数据。

| 服务 | 首期部署建议 | 资源控制原则 |
|---|---|---|
| Caddy | Docker 容器，监听 80/443，自动申请和续期 TLS | 128 MB 上限即可；仅负责 HTTPS、反向代理和静态前端 |
| Node.js API | Docker 容器，内部监听 3000 | 建议 768 MB 上限；不得把会话、队列或图片写入本机内存/磁盘 |
| MySQL 8 | Docker 容器，仅 Docker 内网可访问 | 建议 1–1.25 GB 上限；启用慢查询、每日备份和独立数据卷 |
| 腾讯云 COS | 备案凭证/图片/导出文件 | 浏览器经签名 URL 直传；限制 MIME、大小、对象 Key 和私有读写 |
| 操作系统与余量 | OpenCloudOS 9、Docker、日志缓存和文件系统页缓存 | 至少保留约 1 GB 内存余量；不要把数据库端口暴露至公网 |

## 2. 推荐域名与网络拓扑

建议将前后端拆在明确的子域名上，避免未来微信小程序、管理后台和 API 混用同一个入口。

```text
用户浏览器 / 微信小程序
        │ HTTPS
        ├── app.3dq.site ──► Caddy ──► 静态 React 前端
        └── api.3dq.site ──► Caddy ──► Node.js API ──► MySQL（私网 Docker 网络）
                                                     └── 腾讯云 COS（凭证与导出）
```

`3dq.site` 可在首期 301 跳转至 `app.3dq.site`；也可在业务确认后作为主站使用，但应保持 API 独立为 `api.3dq.site`。DNS 迁移前将记录 TTL 暂时设为 300 秒，待生产稳定后再调整为常规值。HTTPS 证书由 Caddy 管理的前提是对应 A 记录已指向服务器，且安全组/防火墙允许 80 与 443 入站。

| 层级 | 允许公开访问 | 禁止公开访问 |
|---|---|---|
| 腾讯云安全组 | TCP 80、443；TCP 22 仅限固定办公 IP 或受控 VPN | 3000、3306、6379、管理面板端口 |
| OpenCloudOS firewalld | 与安全组一致，形成双层约束 | 所有数据库、容器与调试端口 |
| Docker 网络 | Caddy 可访问 API；API 可访问 MySQL | 浏览器或公网直接访问 MySQL |
| API 跨域 | 仅 `https://app.3dq.site` 与已确认的预发布域名 | `*` 通配跨域、任意来源携带凭据 |

## 3. 服务器安全与运行准备

部署前需先完成以下最小安全基线。执行这些动作会改变 SSH 和防火墙行为，必须确认存在可用的控制台救援入口或第二条 SSH 会话后再实施。

| 类别 | 必须完成的准备 |
|---|---|
| 系统账户 | 新建非 root 的部署账户；只给最小 `sudo` 权限；禁止应用容器以 root 运行 |
| SSH | 使用密钥登录；确认密钥登录可用后再禁用密码登录与 root 远程登录；保留腾讯云控制台救援入口 |
| 系统更新 | 执行系统安全更新；记录内核、Docker、Node、MySQL 和 Caddy 版本，避免“latest”无版本部署 |
| 防火墙 | 腾讯云安全组与 `firewalld` 均只开放 80/443 和受限 22；不对公网开放 MySQL 或 Node 端口 |
| 密钥 | 将数据库口令、JWT/OAuth 密钥、COS 临时凭据和邮件密钥放入服务器受限 `.env` 或密钥服务；不写入 Git、镜像、前端包或聊天记录 |
| 日志 | 应用记录结构化访问/错误日志，掩盖密钥与个人信息；设置日志轮转，防止 3 Mbps 服务器因日志耗尽磁盘 |
| 时间 | 设置上海时区和 NTP 同步；数据库时间统一用 UTC 保存，页面按用户时区显示 |

## 4. 数据库、附件和备份策略

首期建议单机 MySQL 8，使用具名 Docker 数据卷持久化。数据库不是前端 Store 的镜像，而应成为唯一事实来源：金额使用整数分，订单单价/成本/渠道模板保留快照，退款与更正遵循服务端事务和审计规则。

| 项目 | 首期策略 | 验收标准 |
|---|---|---|
| Schema 迁移 | 通过版本化 SQL/Drizzle migration 执行 | 测试环境先跑通；生产有执行时间、版本和回滚记录 |
| 备份 | 每日逻辑备份上传 COS；至少保留 7 个每日恢复点 | 每月在独立数据库实际恢复一次，而非只检查文件存在 |
| 附件 | COS 私有桶、签名上传、数据库仅存 Key/大小/MIME/哈希 | 图片不经过 3 Mbps 应用服务器转发；禁止公开桶 |
| 数据导出 | 支持工作区范围的 CSV/JSON 受控导出 | 导出操作写入审计日志并使用短期下载 URL |
| 灾难恢复 | 服务器异常时，从代码镜像、环境变量备份、MySQL 备份和 COS 元数据恢复 | 有书面 RTO/RPO 目标；首期建议明确为“日备份、可人工恢复” |

## 5. 迁移流程：先建后端，再迁数据，再切流量

当前项目仍是 localStorage 原型，服务器准备完成后**不能直接部署并获得云端账本**。需要先完成 Node.js 后端、数据库 Schema、受保护 API 和前端远端状态接入。迁移过程应保持原站可回退，禁止把用户浏览器中的真实账本静默覆盖。

| 阶段 | 动作 | 退出/回滚条件 |
|---|---|---|
| 1. 基础设施 | 配置 Docker、Caddy、MySQL、COS、域名和 TLS；先部署空健康检查 | 任一安全/健康检查失败时不改生产 DNS |
| 2. 预发布 | 使用 `staging.3dq.site` 和独立数据库进行登录、分录、订单、退款、备份恢复测试 | 未通过迁移、权限、恢复或性能验收时不进入生产 |
| 3. 数据导出 | 在旧版增加“导出本机账本”功能；用户下载并确认导出包 | 未取得确认导出包时，不删除或重置 localStorage |
| 4. 预览导入 | 服务端解析导出包，展示条数、金额汇总、异常项与预览；用户确认后导入 | 校验失败、分录不平、订单快照缺失时拒绝导入 |
| 5. 灰度上线 | 先为管理员/测试工作区启用云端写入；持续观察错误率、延迟、备份结果 | 发生数据一致性问题时切回旧版只读与备份恢复 |
| 6. DNS 切换 | 将 `app.3dq.site`/`api.3dq.site` 指向生产服务器；保留现有站点为只读回退入口至少 7–14 天 | DNS/HTTPS/API 验收失败可恢复旧记录，不删除原站 |

## 6. 上线前必须补齐的信息

下列信息尚未确认。它们会影响具体命令、数据库布局、DNS 记录与安全组，确认前不应连接或改动服务器。

| 待确认项 | 需要的内容 |
|---|---|
| SSH | 公网 IP 或安全访问方式、登录用户名、是否已配置密钥登录。不要通过聊天发送密码或私钥。 |
| 域名 DNS | `3dq.site` 的 DNS 控制权是否在腾讯云或其他注册商；是否允许创建 `app`、`api`、`staging` 子域。 |
| 系统磁盘 | 系统盘/数据盘容量、是否 SSD、是否已有业务数据。建议应用和 MySQL 数据卷预留至少 40–60 GB SSD。 |
| 数据库选择 | 首期是否接受 MySQL 8 与应用同机部署；如使用腾讯云受管数据库，需要提供内网连接规划而非密码。 |
| 文件需求 | 是否要保存凭证图片、大小上限和保留期限；这决定 COS 桶、生命周期规则和上传体验。 |
| 真实数据 | 现有 localStorage 是否已有必须迁移的真实账本；若有，需先开发导出/预览导入。 |
| 发布节奏 | 是否先上线 Web 管理端，还是同时准备微信小程序 API；是否需要预发布域名。 |

## 7. 当前建议

建议先把服务器按本清单完成“可安全承载应用”的基础设施准备，同时在现有项目中开发 Node.js 全栈账本和可确认的 localStorage 导出/导入。不要先在服务器上安装大量业务组件，也不要先把 `3dq.site` 指向当前静态原型；这样可以将安全、数据迁移和业务开发拆开验证，保留明确的回滚空间。

### 首次连接后会执行的顺序（需再次确认）

1. 检查系统版本、磁盘、内存、Docker 是否已安装以及腾讯云安全组当前规则，不进行写入变更。
2. 创建受限的 `deploy` 账户并验证其 SSH 密钥登录；在第二个会话验证成功前，绝不关闭 root 访问。
3. 更新系统补丁，安装锁定版本的 Docker Engine、Compose 插件和基础工具；创建 `/opt/cost-book`、数据卷和受限环境文件目录。
4. 在腾讯云安全组和 `firewalld` 中仅允许 80/443 公开访问，并将 22 限制为您的固定办公公网 IP 或受控 VPN；不开放 3000、3306 等应用端口。
5. 部署 Caddy、Node 健康检查容器和 MySQL，但数据库仅在 Docker 内网可访问；在此阶段不处理真实账本数据。
6. 经您确认后添加 DNSPod A 记录，由 Caddy 申请 HTTPS 证书；完成 `https://app.3dq.site/health` 与 `https://api.3dq.site/health` 的外网验证。
7. 最后才接入正式 Node.js 账本、COS、备份任务和生产工作区；若任一验收失败，停止在当前阶段并保留上一步可运行状态。
