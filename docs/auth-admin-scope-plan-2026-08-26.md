# 双验证码与管理员专用后台实施补充方案

**已确认范围：**支持**邮箱验证码与短信验证码**；用户、店铺、模块维护和数据分析后台仅向**平台管理员**开放。  
**不变边界：**普通店铺用户继续只访问自己的经营工作区；任何认证、后台或分析功能不得读取、导出或修改未授权的账本、订单、图片凭证或个人资料。

## 一、认证体验的目标状态

认证不应要求用户理解底层通道，只需要在合适的时机提供可信、可恢复的验证方式。账号以内部 `userId` 为唯一身份；邮箱和手机号作为可绑定、可验证的联络方式。新用户创建账号时至少验证其中一个通道，随后在“账户安全”中可绑定另一个通道。这样既提供邮箱与短信双通道，也不让首次引导被两个必填字段阻断。

| 场景 | 默认通道 | 可切换通道 | 结果 |
|---|---|---|---|
| 创建店铺 | 用户输入的邮箱或手机号 | 已输入另一可用通道 | 验证成功后创建账号与工作区。 |
| 登录 | 密码登录；新设备或风险操作触发验证 | 已绑定邮箱/手机任选其一 | 通过后建立会话并写入审计。 |
| 找回密码 | 用户选择已绑定的邮箱或手机号 | 另一已绑定通道 | 验证后设置新密码，旧会话失效。 |
| 修改邮箱/手机 | 当前已验证通道 | 另一已验证通道 | 先验证旧联系方法，再验证新联系方法。 |
| 高风险操作 | 默认优先强度更高或最近验证通道 | 已绑定另一通道 | 例如管理员角色变更、API Key、导出范围变更。 |

密码登录保持可用；验证码不是替代密码的临时补丁，而是用于**账户验证、找回与高风险确认**的统一安全能力。

## 二、双通道验证码服务设计

### 1. 统一挑战模型

不要分别开发“邮件验证码”和“短信验证码”的业务逻辑。使用统一的验证挑战模型，只将通道差异放入 provider 适配层。

| 字段/能力 | 说明 |
|---|---|
| `channel` | `email` 或 `sms`。 |
| `purpose` | `sign_up`、`sign_in_verify`、`password_reset`、`bind_contact`、`high_risk_action`。 |
| `destinationHash` | 联系方式的不可逆规范化哈希，用于限流和检索；明文仅在需要发送时短暂使用。 |
| `codeHash` | 验证码只存哈希，永不写入日志或分析事件。 |
| `expiresAt`、`consumedAt` | 短有效期、一次性使用。 |
| `attemptCount`、`requestCount` | 支撑校验失败与重发限制。 |
| `context` | 仅保存最小上下文，如待绑定用户或密码重置会话标识，不保存账本内容。 |

### 2. Provider 适配层

| 通道 | 适配接口 | 服务商在实现前需确认的条件 |
|---|---|---|
| 邮件 | `sendEmailOtp(destination, template, code)` | 发信域名、SPF/DKIM、模板审批、退信处理。 |
| 短信 | `sendSmsOtp(destination, template, code)` | 短信服务商、签名、模板审批、发送地区、频率和单价。 |

实现时仅在服务端保留服务商密钥；客户端只调用受限的 `requestVerification` 和 `confirmVerification` 过程。密钥通过项目密钥管理注入，不进入前端、Git 或日志。

### 3. 最低安全规则

| 项目 | 规则 |
|---|---|
| 验证码 | 六位随机码，服务端哈希保存。 |
| 时效 | 短时有效；过期、消费或密码重置成功后不可复用。 |
| 限流 | 按目的、联系方式哈希、用户、IP 与设备进行多层限流；重发有冷却时间。 |
| 失败 | 连续失败后暂时锁定挑战；所有提示使用通用文案，避免枚举邮箱或手机号。 |
| 审计 | 记录请求、成功、失败、锁定和通道切换，但不记录明文联系方式、验证码、密码或令牌。 |
| 恢复 | 重置密码成功后撤销既有会话；修改联系信息需要先验证旧通道再验证新通道。 |

## 三、管理员专用后台

后台不作为店铺端的一级导航，也不由普通 owner 访问。前端路由隐藏只是一层体验控制；真正的边界由服务端现有 `adminProcedure` 强制执行。[1]

| 后台模块 | 管理员可做 | 明确禁止 |
|---|---|---|
| 用户与账号 | 搜索账号、查看验证状态、冻结/恢复、重置引导、查看审计。 | 查看密码、验证码、会话令牌、私有凭证内容。 |
| 店铺工作区 | 查看工作区状态、行业、成员数、最后活跃时间。 | 直接改写流水、订单、SKU、成本卡和历史报表。 |
| 版本与模块维护 | 查看发布版本、迁移、功能开关、模块状态与错误摘要。 | 直接跳过迁移、覆盖生产密钥、无审计修改配置。 |
| 数据质量 | 查看缺分类、缺供应商关联、无成本 SKU 等匿名聚合。 | 下钻至未经授权的具体账单、商户、备注或图片。 |
| 产品分析 | 查看激活、留存、功能使用、错误率等聚合指标。 | 收集金额、分类名称、原始交易、凭证或密码。 |

### 管理员路由与审计

管理端建议从独立的受保护入口进入，例如 `/admin`。所有读取和写入过程都需要 `adminProcedure`；每次管理员查询敏感元数据、改变用户状态、发布配置或导出汇总都产生审计事件。

```text
浏览器管理端
      ↓
管理员会话 + 服务端角色确认
      ↓
adminProcedure
      ↓
受限查询/操作 + 审计事件
      ↓
聚合结果或最小必要状态
```

普通用户即使猜到管理路由，也只能得到通用的无权限响应，不暴露用户、工作区或配置是否存在。

## 四、数据模型与 API 增量

| 阶段 | 数据/接口 | 说明 |
|---:|---|---|
| A | `account_contacts`、`verification_challenges`、`security_events` | 支撑邮箱/手机绑定、验证挑战与安全审计。 |
| B | `admin_audit_events`、受控用户状态字段 | 支撑管理员动作、冻结/恢复与可追溯性。 |
| C | `feature_flags`、`release_records`、`content_configs` | 支撑模块更新、灰度、公告与首次引导内容。 |
| D | `product_events` 的匿名/聚合写入路径 | 支撑产品激活、功能使用、错误率和数据质量，不采集账本明细。 |

每张表都按“schema → migration → 最小 DB helper → tRPC contract → 管理端/用户端 → 单元回归”的顺序实现。公开 API 保持在后续阶段，且不会直接暴露内部 tRPC 过程。

## 五、实施顺序

| 阶段 | 交付物 | 验收核心 |
|---:|---|---|
| 1 | 认证视觉统一、邮箱/手机绑定状态、验证码挑战模型与邮件 provider。 | 注册、验证、找回密码和重发限流完整；无敏感日志。 |
| 2 | 短信 provider、通道选择与双通道恢复。 | 邮箱和短信成功/失败/过期/锁定分支一致；服务商故障有安全降级。 |
| 3 | 账户安全页、设备会话、管理员路由和管理员审计。 | 非管理员服务端拒绝；管理员操作可追溯。 |
| 4 | 管理后台的用户、店铺、发布、健康、数据质量模块。 | 后台只读优先、修改受控、无账本明细泄露。 |
| 5 | 匿名产品事件和聚合分析面板。 | 事件字典、隐私过滤、保留期与指标口径可审计。 |
| 6 | API Key/OAuth、`/api/v1`、Webhook 和集成导入。 | scope、限流、幂等、撤销和审计完备。 |

## 六、开始实现前需要的配置

开始阶段 1/2 时，需要分别提供或确认：邮件发送服务与发信域名；短信服务商、签名、模板和服务地区；验证码文案及同意隐私条款的页面文案。服务商密钥只在明确选定后通过安全配置注入。
