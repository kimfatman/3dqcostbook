# P3 定时备份 Worker 守护进程与失败重试实现方案

**文档日期：** 2026-08-28  
**适用分支：** `agent/backend/admin-maintenance-backend`  
**适用阶段：** P3 定时备份管理  
**作者：** Manus AI

## 1. 目标与边界

P3 已经提供备份计划、备份运行记录和管理员排队接口。下一步需要一个受控的后台 worker 按计划发现到期任务、执行备份、记录结果并在失败时有限重试。本方案只定义 worker 和失败处理的实现边界，不在当前会话启动生产 worker、不执行生产备份、不读取或修改生产运行时密钥。

worker 的职责是处理已经通过服务端授权并进入队列的 `backup_runs`，将可验证的数据库备份产物写入受控私有存储，并把执行状态更新为 `succeeded` 或 `failed`。worker 不接受浏览器传入的存储路径、数据库连接串、COS 凭据或命令参数；所有存储目标和凭据必须来自服务端运行时密钥管理。管理页面只能看到计划、运行状态、时间、字节数和脱敏错误摘要。

> **重要边界：** `admin.backups.schedules.runNow` 只创建 `queued` 记录。它不能在 HTTP 请求中直接执行 mysqldump、COS 上传、恢复或删除操作。

## 2. 可选运行方式

备份 worker 属于确定性后台任务，不应通过每次启动完整 AI 会话的方式执行。项目应在以下方案中选择一个，并由统筹/发布 Agent 在部署前完成安全、成本和恢复演练复核。

| 方案 | 运行方式与适用场景 | 主要权衡 | 成本 | 部署复杂度 |
|---|---|---|---|---|
| 托管定时触发 + 短时 worker | 由托管平台的 cron/Heartbeat 每分钟或每五分钟唤起一个幂等 worker；worker 扫描到期计划并处理有限批次 | 无常驻进程，成本和运维较低；需要严格控制单次超时、批次和并发 | 使用量计费，通常最低 | 中 |
| 持续 worker 守护进程 | 一个持续运行的服务每 30–60 秒扫描计划和队列，适合备份耗时较长、需要稳定吞吐的场景 | 任务调度更直接、重试更稳定；需要常驻实例、健康检查和自动重启 | 使用量计费，常驻资源更高 | 中高 |
| 外部云任务队列/托管备份 | 将队列和存储交给已有云厂商任务队列、数据库备份或对象存储生命周期服务 | 可靠性和审计能力较强；平台绑定、权限配置和跨系统排障成本更高 | 取决于云厂商和存储量 | 高 |

在没有特殊运行时限制时，第一种方式更容易与当前 WebDev 项目整合；如果单次备份可能超过托管请求限制，第二种方式应使用单一持久 worker；只有在需要数据库厂商原生备份、跨区域复制或超出单实例资源边界时，才考虑第三种方式。无论选哪种方式，worker 都必须依赖数据库中的租约、唯一运行标识和状态机，而不能依赖进程内存防重复。

## 3. 推荐的任务生命周期

备份任务应采用显式状态机。状态只能按允许的方向流转，任何非法跳转都应记录为失败并报警，不得静默覆盖原状态。

| 当前状态 | 允许的下一状态 | 触发条件 |
|---|---|---|
| `queued` | `running`、`cancelled` | worker 成功取得租约，或管理员在开始前取消 |
| `running` | `succeeded`、`queued`、`failed`、`cancelled` | 备份成功、可重试失败、达到重试上限、受控取消 |
| `succeeded` | 无 | 终态；只能由保留策略清理相关产物，不修改历史结果 |
| `failed` | `queued`、`cancelled` | 人工重试或策略允许的自动重试 |
| `cancelled` | 无 | 终态，不再自动执行 |

当前 `backup_runs` 表已经保存 `queued/running/succeeded/failed/cancelled`、开始/完成时间、写入字节数和脱敏错误摘要。实现 worker 时应补充以下字段：`attempt`、`nextAttemptAt`、`leaseUntil`、`workerId`、`idempotencyKey`、`sourceSnapshot`。其中 `sourceSnapshot` 仅保存备份范围和 schema 版本等元数据，不保存数据库内容或凭据。

如果不希望立即扩大表结构，也可以先把 `attempt`、`nextAttemptAt` 和租约信息放在独立的 `backup_run_attempts` 表中。独立表更适合保留每次失败原因和延迟，但查询与迁移数量更多。最终选择必须在迁移前由统筹/发布 Agent 确认。

## 4. 调度发现与租约算法

worker 每轮只处理有限数量任务，例如每次最多 5 个 `queued` 任务和 5 个到期重试任务。它首先读取状态为 `enabled` 且 `runAt` 到期的计划，并使用计划标识、计划窗口和时区计算一个稳定的 `idempotencyKey`，例如 `scheduleId:2026-08-28T02:30+08:00`。同一计划同一时间窗口只能创建一个运行记录。

取得任务时必须使用数据库事务或条件更新完成租约：

```sql
UPDATE backup_runs
SET status = 'running', workerId = :workerId,
    leaseUntil = DATE_ADD(NOW(), INTERVAL 15 MINUTE),
    startedAt = COALESCE(startedAt, NOW()),
    attempt = attempt + 1
WHERE id = :runId
  AND status = 'queued'
  AND (nextAttemptAt IS NULL OR nextAttemptAt <= NOW());
```

只有受影响行数为 1 的 worker 才能执行任务。租约超时后，另一个 worker 可以将过期的 `running` 任务重新排队，但必须先记录 `lease_expired` 事件并增加尝试次数。备份执行时间应小于租约时长；如果无法保证，应采用心跳续租，而不是盲目延长初始租约。

在 MySQL 条件更新和唯一键不可同时保证时，worker 必须把“创建运行记录”和“取得租约”都视为幂等操作。发生唯一键冲突时读取已有记录，不创建第二份备份，也不把冲突误报为执行失败。

## 5. 失败分类与重试策略

失败处理必须先分类，再决定是否重试。错误摘要只允许写入固定分类和脱敏信息，例如 `database_unavailable`、`storage_timeout` 或 `checksum_mismatch`；不能写入 SQL、连接串、Token、对象存储签名 URL、完整路径或请求头。

| 错误类别 | 示例 | 是否自动重试 | 默认上限 | 处理方式 |
|---|---|---:|---:|---|
| 临时数据库错误 | 连接超时、连接池暂时耗尽、只读切换窗口 | 是 | 5 次 | 指数退避并加抖动 |
| 临时存储错误 | COS 5xx、网络超时、限流 | 是 | 5 次 | 指数退避；上传使用分片和校验 |
| 任务租约失效 | worker 被终止或超过租约 | 是 | 2 次额外尝试 | 重新排队并记录租约事件 |
| 校验失败 | 备份校验和不一致、产物为空 | 谨慎 | 2 次 | 重做一次；再次失败进入人工处理 |
| 参数或配置错误 | 不支持时区、目标不存在、格式错误 | 否 | 0 | 立即 `failed`，管理员修复计划 |
| 权限/凭据错误 | 密钥无效、无 Bucket 权限 | 否 | 0 | 立即 `failed`，只记录脱敏摘要并告警 |
| 磁盘/配额不足 | 存储配额耗尽或本地临时目录不足 | 否或一次 | 1 次 | 先暂停计划，避免连续失败 |
| 进程终止 | OOM、SIGTERM、节点重启 | 是 | 按原类别 | 依赖租约回收，不在退出钩子中执行长任务 |

建议延迟公式为：

```text
backoff = min(30 minutes, 30 seconds × 2^(attempt - 1)) + random(0, 20 seconds)
```

在同一 `idempotencyKey` 上设置最大尝试次数，避免重启 worker 重新把计数归零。达到上限后，任务置为 `failed`，计划默认保持 `enabled` 但进入告警状态；如果连续两个计划窗口失败，则自动将计划置为 `paused` 并写入管理员审计，防止无效配置产生无限错误。是否自动暂停必须做成明确的全局配置，不应隐藏在代码常量中。

## 6. 备份产物、校验与保留

推荐产物流程是：读取一致性快照、流式压缩、计算 SHA-256、写入私有对象存储临时键、完成后原子标记为正式键，再写入成功记录。数据库成功记录必须在对象存储完成校验之后写入；如果数据库写入失败，后续清理 worker 可以依据幂等键回收孤儿对象。

备份产物键不得使用用户可控路径，格式应由服务端生成，例如：

```text
private-backups/{scheduleId}/{windowStart}/{runId}.sql.gz
```

worker 只在固定前缀下写入，不允许 `..`、绝对路径、外部 Bucket 或浏览器传入的任意存储键。保留策略应先删除过期产物，再更新数据库中的清理审计；清理失败不能删除成功运行记录。删除对象属于不可逆动作，生产环境必须配置二次确认或由经授权的生命周期策略执行，并保留删除结果和影响范围。

校验至少包含非零字节数、SHA-256 和可选的压缩流完整性。生产恢复演练应从最近一次成功备份的副本执行到隔离数据库，禁止直接覆盖生产库。恢复接口不属于本 P3 worker，需单独设计审批、双人复核和回滚方案。

## 7. 守护进程结构

worker 可以按以下模块拆分：

| 模块 | 责任 |
|---|---|
| `scheduler` | 根据 enabled 计划和时区计算到期窗口，使用幂等键创建 queued run |
| `claimer` | 通过条件更新取得租约，限制批次和全局并发 |
| `executor` | 执行一致性快照、压缩、上传和校验；不接收浏览器参数 |
| `retry-policy` | 分类错误、计算退避、更新 nextAttemptAt 和最终状态 |
| `retention` | 按保留日清理过期产物，单独限速并记录审计 |
| `health` | 暴露最近轮询、队列深度、运行数、失败数和最后成功时间 |
| `audit` | 写入计划创建、排队、取得租约、重试、成功、失败、取消和清理事件 |

主循环不应使用无界并发。建议全局并发默认为 1，待恢复演练证明数据库、压缩和存储容量后再提高到 2。每轮结束后等待固定间隔；关闭时停止领取新任务，等待当前任务在短超时内完成，超过超时则释放或等待租约自然过期，不强行把未完成任务标记为成功。

## 8. 监控与告警指标

管理员监控页面只显示运营所需的聚合指标。建议记录以下指标样本：`backup.queue_depth`、`backup.running_count`、`backup.success_count`、`backup.failure_count`、`backup.retry_count`、`backup.last_success_age_seconds`、`backup.duration_ms`、`backup.bytes_written` 和 `backup.lease_expiry_count`。指标值应为整数或有限数值，标签只使用固定 metric key，不记录用户输入、完整 URL、SQL 或凭据。

告警至少包括：连续两个计划窗口失败、队列等待超过阈值、运行租约过期、成功备份距当前超过保鲜阈值、校验失败、存储配额不足和 worker 心跳消失。告警内容只带计划 ID 的不可逆短标识、状态和时间，不带敏感路径或密钥。

## 9. 审计与安全要求

worker 只能使用专用最小权限服务身份：读取待处理队列、更新备份运行状态、写入固定私有前缀、读取必要的数据库快照权限、写入指标和管理员审计。它不应拥有用户管理、全局配置发布、迁移执行或生产恢复权限。

每一次状态变化都必须具备 `actor` 或 `workerId`、`requestId/idempotencyKey`、目标运行 ID、前后状态、尝试次数、结果分类和时间。错误写入前进行固定字段白名单过滤。管理端查询接口继续使用现有 `adminProcedure`，普通商家端不得发现或调用 worker 管理操作。

任何暂停计划、取消排队任务、清理备份或改变重试策略的管理动作都需要服务端二次确认和管理员审计。`runNow` 的“已排队”不能被前端显示成“已完成”。浏览器永远不能获得 COS 临时凭证、数据库连接信息、完整对象存储 URL 或备份内容。

## 10. 验收标准

实现 worker 前，必须具备以下自动化和演练门槛：

| 验收项 | 通过标准 |
|---|---|
| 幂等性 | 同一计划窗口重复触发只产生一个运行记录和一个正式产物 |
| 并发 | 两个 worker 同时领取时只有一个获得租约，另一个安全退出或等待 |
| 失败重试 | 临时错误按退避策略重试，永久错误不重试，达到上限进入 failed |
| 租约恢复 | worker 被杀后任务不会永久卡在 running，过期租约可重新排队 |
| 校验 | 空产物、压缩损坏和校验和不一致不能进入 succeeded |
| 脱敏 | 测试响应、日志、审计和错误摘要不出现 Token、密钥、连接串或签名 URL |
| 权限 | 未登录、member、暂停管理员均无法访问管理 worker 接口 |
| 状态 | 前端能区分 queued、running、succeeded、failed、cancelled |
| 保留 | 过期对象清理有边界、有审计，不能删除成功运行记录本身 |
| 恢复 | 在隔离数据库完成定期恢复演练，生产库不被覆盖 |
| 质量门禁 | `pnpm check`、`pnpm test`、`pnpm build` 按项目环境完成并记录结果 |

## 11. 分阶段实施顺序

第一步只增加租约、重试和指标所需的 schema 与非破坏性迁移，生成 SQL 后审阅，不执行生产迁移。第二步实现纯函数形式的退避策略、错误分类、幂等键和状态机，并用 Vitest 覆盖边界。第三步实现单进程 worker 的 dry-run 模式，只领取任务但不连接真实存储，验证并发和恢复逻辑。第四步接入测试环境私有存储，完成最小权限、校验、保留和故障注入演练。第五步经统筹/发布 Agent 明确授权后，才部署生产 worker；生产首次运行应保持低并发并观察至少一个完整计划周期。

当前 P3 后端分支只提供管理 API 和队列记录，尚未实现以上 worker、真实备份执行或生产调度。任何把 `queued` 任务交给生产 worker 的动作都必须在单独的发布审查中确认。
